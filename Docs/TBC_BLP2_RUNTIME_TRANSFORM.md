## Reverse-engineering state

`0x005B1BA0` is VERIFIED as a BLP2 magic/version parser. Descriptor construction/use sites `0x00453FF0`, `0x004544A0`, `0x00455EF0`, and `0x004561F0` are VERIFIED instruction sites. They are not verified hook boundaries.

New static disassembly evidence from the supplied build-8606 `Wow.exe`:

- `0x005B3170` is a caller of `0x005B1BA0`. It obtains a source pointer through calls at `0x00657590`, `0x00654E00`, and `0x00655290` before passing that pointer to the BLP parser. Those calls are VERIFIED as instruction sites, but their storage APIs, allocation contracts, and interface-texture use are UNKNOWN.
- The parser copies the header into its object but also retains the source pointer at object offset `+0x498`. A temporary transformed buffer passed directly to this parser would therefore be unsafe until the complete subsequent use and release path is traced.
- `0x005B3281` checks the parsed encoding byte at object offset `+0x0C`. Encoding `2` is routed through format-index checks; encoding `3` follows a separate branch involving the fifth stack argument at `+0x18`. This is VERIFIED branching evidence, not proof that the instruction itself rejects encoding 3.
- `0x005B32D4` calls `0x005AF040` on one branch; `0x005B3327` handles a pointer-relocation branch. The exact clean-failure instruction is still UNKNOWN.

`0x005AF040` is now VERIFIED as a size/offset-table writer, **not** a texture allocator: it calls `0x005AEF40` to obtain a level count, writes pointers into the caller-provided table at `0x005AF06B`, and advances each level by the size returned from `0x005AEE80`. The latter shifts dimensions by mip index, clamps to at least 1, and applies block-size rules for certain format indices. The precise mapping of every format index and why encoding 3 takes a different branch are still UNKNOWN. In particular, a branch to this table writer does not by itself prove the stock render succeeded or failed.

Further static xrefs show that `+0x498` is not merely a parser-time temporary. `0x005B2C50` checks it and adds mip offset `[object+index*4+0x18]` to it at `0x005B2C98`; `0x005B2F70` makes the same base-plus-mip calculation at `0x005B2FC2`. Both are VERIFIED payload access instruction sites. The encoding-3 case in `0x005B2C50` can return the direct source mip pointer at `0x005B2CCA`/`0x005B2CD7`. That is strong static evidence that source bytes must survive after header parsing and into mip access. It does not prove which higher-level caller uses that return or how long the parser object itself lives.

`0x005B3327` is VERIFIED as a pointer-relocation loop: after checking a nonzero table entry, it reads `+0x498`, adds a stored offset to that base, and writes the resulting pointer into a separate output object until a zero entry. `0x005B3312` then clears the `+0x498` member on this path. That is a pointer clear, not evidence that the underlying file allocation is released there. The destination object's ownership and later pointer use remain UNKNOWN.

`0x00655290` is VERIFIED as a destructor/release-like routine for the source-acquisition handle: it calls several cleanup functions on object fields and frees the 0x44-byte object at `0x00655316`. It is called by `0x005B3170` *before* `0x005B1BA0`. It does not release the separate global BLP data allocation described below.

`0x00654E00` is VERIFIED as a multi-branch, six-argument read/copy routine. Its object type discriminator at `[object]` dispatches among several backends; one branch calls `0x00659F80`, another calls `0x0067CA60`. The destination is the global data buffer described below; exact backend semantics and error details remain UNKNOWN. `0x00657590` is VERIFIED as an acquisition routine with an output pointer written to zero on entry; its exact archive/cache responsibility remains UNKNOWN.

### Reusable source-buffer allocation and release

The `0x005B3170` caller reads the acquired object's size through `0x00654080` (`0x005B31C1`), then calls `0x004316B0` on the global buffer object at `0x00D43118` (`0x005B31CC`). The buffer's current size and data pointer are read at `0x00D4311C` and `0x00D43120` and supplied to `0x00654E00` at `0x005B31EB`. The same `0x00D43120` data pointer is passed to the BLP parser at `0x005B31FF`-`0x005B3202`. These are VERIFIED instruction-level relationships.

`0x004316B0` is a capacity/size routine. When a larger capacity is needed it calls `0x00431430`; that routine replaces the buffer data pointer using `0x00644260`, which is an allocator/reallocator path and can move/free the old allocation. `0x00884D40` frees the global buffer pointer through `0x00644230` on shutdown. Thus the underlying byte buffer is a **reusable global allocation**, not memory owned by the 0x44-byte acquisition handle destroyed at `0x00655290`. A subsequent larger read may relocate it; a subsequent read may overwrite it even without relocation. Whether BLP objects or relocated mip pointers ever survive such a read remains UNKNOWN.

Call xrefs show `0x0045453F` invokes `0x005B3170`, and that caller later invokes `0x005B2E20` at `0x004546CE` before its parser object's cleanup at `0x004546E1`. `0x005B2E20` invokes the mip accessor `0x005B2C50`. This is VERIFIED synchronous use in **that caller**, but does not establish every caller, re-entrancy/threading, cache placement, or that the controlled Interface request reaches this path.

The format selection in `0x00454565` checks the parsed encoding byte against `2`. Encoding 3 follows the default selection path rather than an immediate zero return. The caller then invokes `0x005B2E20` and returns zero only if that later call returns zero (`0x004546D3`-`0x004546DB`). This identifies a possible zero-return convergence in this **separate static route**, not the cause of the fresh controlled BGRA8 visual corruption.

### Partial ownership graph (static evidence only)

```text
0x005B3170 caller
  -> 0x00657590 acquisition (handle semantics UNKNOWN)
  -> 0x00654080 size query
  -> global 0x00D43118 buffer resize via 0x004316B0
       -> 0x00431430 / 0x00644260: reallocatable data at 0x00D43120
       -> 0x00884D40: data release at shutdown
  -> 0x00654E00 read/copy into global data
  -> 0x00655290 handle/object cleanup before parser
  -> 0x005B1BA0 header parse
       -> parser object +0x498 = global data pointer
       -> 0x005B2C50 / 0x005B2F70: source base + mip offset
       -> 0x005B3312: member cleared on one later path
  -> next read may overwrite/reallocate global data: timing UNKNOWN
```

This is still **not** a safe replacement lifetime model. The allocator and shutdown release are identified, but the relative timing of all parser/mip uses versus reuse or reallocation of the global data—and the controlled Interface path—remain unverified. No byte-replacement hook is qualified.
